## 1. Up to 2 missing premises

### Premise 1: “The system English dictionary” is not one stable thing

The plan notices machine variance but never settles two behaviors:

- A Mac may prefer French or German spell-checking while EnviousWispr positively identifies English dictation. The oracle must explicitly choose an installed English dictionary. It must never use the user’s currently selected spell-check language or pass `nil`.
- `NSSpellChecker.learnWord` changes the shared per-user dictionary. Learned words are disproportionately likely to be names, brands, and technical spellings. Treating them as ordinary lowercase words weakens the exact safety boundary this design needs. EnviousWispr Custom Words already provide the explicit protection path.

Drop this into §3 after “The fail-open trap”:

> ### English selection and per-user dictionary state
>
> The oracle never uses `NSSpellChecker.language`, the user’s currently selected spell-check language, or a `nil` language argument. It filters `NSSpellChecker.availableLanguages` to identifiers whose normalized base language is `en`, sorts them for deterministic selection, and chooses the first. If no English identifier exists, the oracle is unavailable and keeps the capital. Therefore English dictation still uses an English dictionary when the Mac’s preferred spell-check language is French, German, or another language.
>
> Learned words are not treated as ordinary lowercase evidence. Before accepting the dictionary result, the oracle checks `NSSpellChecker.hasLearnedWord(lowercaseWord)` and refuses learned entries with `.learnedWord`. Learned entries are likely to be names, brands, and technical spellings; the explicit EnviousWispr Custom Words path remains the authority for preserving those spellings. The oracle owns a fresh spell-document tag and never imports another document’s ignored-word list.

Add this exact enum case:

```swift
case learnedWord = "learned_word"
```

Use this exact resolver:

```swift
static func resolveEnglishLanguage(from availableLanguages: [String]) -> String? {
  availableLanguages
    .filter { identifier in
      identifier
        .replacingOccurrences(of: "_", with: "-")
        .split(separator: "-", maxSplits: 1)
        .first?
        .lowercased() == "en"
    }
    .sorted()
    .first
}
```

And require this decision before accepting the spell result:

```swift
guard !spellChecker.hasLearnedWord(lowercaseWord) else {
  return .refuse(.learnedWord)
}
```

The grounded round should verify the exact API behavior, especially whether ignored words can affect a fresh document tag.

An update replaces that bundle, so an already-installed user needs no cleanup or data migration. Also tighten “keep the capital.” It should mean only that leading-case repair does not lowercase the word. Spacing, duplicate removal, or terminal-period placement may still change the candidate afterward.

## 2. One placement challenge

The strongest alternative is a new leaf module containing the AppKit/NaturalLanguage implementation, with PostProcessing owning only a narrow protocol and Pipeline injecting the implementation at its one production caller.

Its shape would be:

```swift
public enum EnglishWordDecision: Equatable, Sendable {
  case mayLower
  case refuse(CursorInsertionRepair.CaseSkipReason)
}

public protocol EnglishWordDeciding: Sendable {
  func decide(
    word: String,
    leftContext: String,
    payload: String
  ) -> EnglishWordDecision
}
```

A new `EnviousWisprLanguageServices` target would implement that protocol using `NSSpellChecker` and `NLTagger`. Pipeline would construct it and pass it into repair. PostProcessing and the alias CLI would remain free of AppKit and NaturalLanguage.

The real cost is substantial:

- A new target in both package/build definitions.
- A new cross-module public protocol and decision type.
- Pipeline composition changes at the heart-path caller.
- A module-boundary change that raises this from MEDIUM to REFACTOR.
- More wiring and build validation for one implementation and one consumer.

It does not beat the current plan. The current owner is the actual casing feature owner, the system calls are synchronous and tiny, and the proposed test seam keeps unit tests isolated. The plan should nevertheless replace its weak “two-line import” argument with the real comparison.

Replace §3b’s opening paragraph with:

> `EnglishWordOracle` remains in PostProcessing because it implements PostProcessing’s own leading-case policy, has one consumer inside `CursorInsertionRepair`, holds no app or pipeline state, and returns a synchronous value. The strongest alternative is a new leaf `EnviousWisprLanguageServices` module implementing a public `EnglishWordDeciding` protocol, constructed and injected by Pipeline. That would preserve PostProcessing’s present framework purity, but it requires a new target in both build systems, new cross-module public API, Pipeline composition changes, and REFACTOR-tier validation for one implementation and one consumer. That structural cost is larger than the boundary benefit here. The AppKit and NaturalLanguage imports are therefore an intentional PostProcessing boundary expansion, not a convenience accident.

## 3. Validation strategy

### Finding: the planned precision gate is both self-authored and internally contradictory

The plan currently says:

- Adversarial precision is 89.5%.
- The adversarial corpus is the gate.
- The gate is at least 90%.
- “Zero damage is the contract.”
- The ship criteria permit two damaged realistic cases.

Those cannot all be the contract.

There is another unresolved fork: if CI runs the real system oracle, the result varies by runner dictionaries, learned words, and NaturalLanguage assets. If CI injects a fake oracle, the precision number no longer measures the system-backed design.

The cheapest honest strengthening is:

1. Freeze a corpus before implementation from an outside source, not examples selected to exercise the proposed rule. Deterministically sample sentence-internal seams from a public-domain English corpus. Original lowercase openers become “should lower”; original internal proper capitals become “must keep.” Preserve the real 20-unit window.
2. Keep CI deterministic. Gate branch behavior, refusal behavior, routing, Custom Words precedence, and exact output using injected fixed answers.
3. Run the real system-service characterization as a pre-ship measurement on the founder’s Mac. Make it advisory in CI. Record OS version, chosen English identifier, tag-scheme availability, counts, and damaged case IDs.
4. Treat the current adversarial and realistic author corpora as diagnostics, not independent validation.

Replace §11.2 from the metric paragraph onward with:

> ### Deterministic tests versus system characterization
>
> CI does not gate a numeric precision score produced by `NSSpellChecker` or `NLTagger`. Those services vary by OS image, installed dictionaries, NaturalLanguage assets, and per-user learned words; making their exact output required would create a flaky gate.
>
> CI instead uses injected, fixed dictionary and lexical-class answers to gate the code contract: every guard order, every accepted word class, every refusal class, missing-service behavior, learned-word refusal, Custom Words precedence, the 20-unit context boundary, and the exact repaired text and rule names. Every refusal case must preserve the payload’s original first grapheme and must not emit `.lowercasedFirst`.
>
> Before implementation, freeze an independent characterization corpus built by deterministic sampling from a named, version-pinned public-domain English source. Sample sentence-internal split points rather than author-selected examples. An originally lowercase first word is a lower candidate; an originally capitalized internal proper word is a keep candidate. Store stable case IDs, the final 20 UTF-16 units of left context, payload, expected class, source/version, sampling seed, and license.
>
> Run the production oracle over that frozen corpus on the founder’s shipping Mac before release. Record the macOS version, selected English dictionary identifier, lexical-class availability, attempted decisions, lower coverage, damaged-name count, and precision. The existing adversarial and realistic author-written corpora remain diagnostic slices and do not independently certify the threshold. CI may run this characterization for information, but a different machine result does not fail CI.

Replace §13 items 2 and 3 with:

> 2. On the frozen independent corpus, the production oracle achieves at least 90% precision on decisions to lowercase when run on the founder’s shipping Mac. Record the exact environment and every damaged case ID.
> 3. The author-written adversarial, realistic, and long-context slices are reported separately as diagnostics. They have no independent pass threshold and cannot override the frozen external corpus.
> 4. Deterministic CI tests cover every acceptance and refusal branch without calling machine-variable system services.
