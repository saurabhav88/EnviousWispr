## Q1. Owner and process boundary

### Where it executes

Production execution is:

1. The main EnviousWispr app constructs both recording drivers (`Sources/EnviousWisprAppKit/App/WisprBootstrapper.swift:335-355`, `:372-405`).
2. The factory builds `KernelFinalizationWiring` and gives its `deliver` closure to the recording kernel (`Sources/EnviousWisprPipeline/KernelDictationDriverFactory.swift:398-431`).
3. `RecordingSessionKernel` is `@MainActor`, and its delivery closure is explicitly `@MainActor` (`Sources/EnviousWisprPipeline/RecordingSessionKernel.swift:187-192`, `:218-226`).
4. After ASR, processing, and storage, the kernel awaits that closure (`Sources/EnviousWisprPipeline/RecordingSessionKernel.swift:2518-2535`).
5. Inside that main-actor closure, the app reads the caret, resolves language, calls `CursorInsertionRepair.repair`, and only then starts paste delivery (`Sources/EnviousWisprPipeline/KernelFinalizationWiring.swift:357-412`, `:426-436`).

So production repair runs **inside the GUI app process, synchronously on the main actor, immediately before paste**.

## Q3. Every current lexicon-dependent decision

There are only two true word-knowledge decisions:

1. **Is word knowledge available?**  
   If not, an otherwise eligible English uppercase opener remains unchanged and reports `caseSkipped:lexicon_unavailable` (`CursorInsertionRepair.swift:457-490`).

2. **Is the first word positively known lowercase?**  
   If absent, it remains capitalized and reports `caseSkipped:not_known_lowercase`; if present, only its first character is lowered (`CursorInsertionRepair.swift:492-497`).

The following do **not** depend on membership or availability:

- Leading spacing: `CursorInsertionRepair.swift:331-339`.
- Language casing gate: `:341-358`.
- Seam duplicate removal: `:371-398`.
- Touching-full-stops removal: `:400-425`.
- Trailing spacing: `:428-445`.

That is normalization reuse, not word knowledge. Removing the type wholesale would therefore touch PR #1804 code even though duplicate detection does not consult its word set.

Today, “lexicon unavailable” means:

## Q4/Q5. Additional naive-swap traps

### 1. Region information has already been discarded

`LanguageRules` reduces the language to two booleans and keeps casing only when the base code is `"en"` (`CursorInsertionRepair.swift:193-209`). `applyLeadingCase` receives no language or locale at all (`:349-356`, `:457-461`).

Therefore the current seam cannot distinguish `en`, `en_US`, and `en_GB` when it reaches word lookup. This is a separate code trap from the dictionary disagreement you measured.

### 2. Nil language is safe only while the existing gate stays intact

`DictationLanguageResolver` deliberately returns nil for short or uncertain input (`DictationLanguageResolver.swift:25-37`, `:62-80`). Nil becomes `LanguageRules.unknown`, which skips casing (`CursorInsertionRepair.swift:199-208`, `:349-353`).

So: **no trap here if the current casing gate remains intact.**

But passing nil directly to `NSSpellChecker` has different semantics: it uses the spell checker’s currently selected language/user preference (`MacOSX.sdk/.../AppKit.framework/Headers/NSSpellChecker.h:150-153`). That would turn an intentional abstention into mutable user state.

### 3. The system spell checker is application-global state

Apple defines exactly one shared spell checker per application (`NSSpellChecker.h:37-48`). It also exposes user-selected language state and learned-word state (`NSSpellChecker.h:150-160`).

That matters in tests and multiple hosts: the app, XCTest process, and AliasRunner each get their own application/process-level singleton state. Your background-thread measurement proves it functions there; it does not make those hosts share one deterministic dictionary state.

### 4. `NLTagger` instances are not concurrently reusable

The SDK explicitly says one `NLTagger` instance must not be used from more than one thread simultaneously (`NLTagger.h:56-60`). Your concurrent `NSSpellChecker` result does not establish the same contract for one shared tagger.

### 5. Lexical-class assets are not guaranteed to exist

The SDK says some scheme/language combinations may be unsupported on the current device (`NLTagger.h:40-42`). It separately says a missing scheme may mean assets are not loaded, and asset requests complete later, potentially on an arbitrary queue (`NLTagger.h:81-90`).

CI performs no availability or asset step (`.github/workflows/pr-check.yml:64-90`, `:177-203`). This is a real trap.

### 6. The available context is much smaller than “the document”

The production reader supplies at most 20 UTF-16 units on either side (`Sources/EnviousWisprServices/PasteService.swift:392-422`, `:446-472`). `CursorInsertionRepair` receives only those bounded windows (`CursorInsertionRepair.swift:20-44`).

Any POS/name result measured with broader context is not automatically evidence for the actual paste-path input.

### 7. First-call work sits directly on the paste path

The delivery closure is main-actor isolated (`KernelFinalizationWiring.swift:127-155`). Caret reading, language recognition, case repair, and only then paste occur sequentially (`:357-412`, `:426-436`).

There is no timeout or error boundary around `CursorInsertionRepair.repair` itself (`:373-412`). Therefore any synchronous spell-service startup or tagger/model initialization adds directly to stop-to-paste latency. Your measured 1.33 ms `NSSpellChecker` cold call shows **no demonstrated spell-checker latency trap on this machine**. It says nothing about a missing or cold lexical-class asset.

### 8. Protected/custom words currently outrank system knowledge

Protected spellings are snapshotted before the first suspension point (`KernelFinalizationWiring.swift:188-201`), passed into repair (`:376-412`), and checked before lexicon availability or membership (`CursorInsertionRepair.swift:474-493`).

So: **no trap here if that order remains unchanged.** A naive rewrite that asks the system first would silently change PR #1804’s protection contract.

### 9. De-duplication order is load-bearing

Leading-case evaluation happens before seam de-duplication (`CursorInsertionRepair.swift:341-398`). The source explains that reversing the order retargets casing onto the second word (`:381-385`).

Changing the word provider must not be treated as isolated from this order. The existing regression test is `CursorInsertionRepairTests.swift:1399-1419`.

### 10. Repaired text feeds later custom-word learning

When a route commits repaired text, that exact repaired payload is emitted to observers (`KernelFinalizationWiring.swift:438-453`). The registry’s planned consumer learns from edits to what was pasted (`Sources/EnviousWisprServices/PasteCompletionRegistry.swift:3-17`).

Therefore machine-dependent casing changes not only visible output but also the baseline later learning compares against. That is broader than the one pasted sentence.

### 11. Sandbox/entitlement concern: no trap here

The shipped app is Developer-ID signed, hardened, and notarized, but it is **not sandboxed**. Its entitlements omit `com.apple.security.app-sandbox` and explicitly describe it as non-sandboxed (`Sources/EnviousWispr/Resources/EnviousWispr.entitlements:21-25`). Release signing enables hardened runtime (`scripts/build-release-dmg.sh:282-344`) and verifies it (`:444-460`).

I found no special NSSpellChecker entitlement in the SDK/API contract. Therefore there is no current App Sandbox entitlement trap for this app. The premise “sandboxed app” does not match the live release configuration.
